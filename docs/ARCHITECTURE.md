# Архитектура Absolert

Стартовое решение от 14 ноября 2026 года. Документ описывает направление разработки,
а не уже существующие пакеты и интерфейсы. Детали уточняются при реализации.

## Назначение и границы

Absolert — пассивная IDS для наблюдения за попытками вторжения на внешнем периметре
промышленной вычислительной сети. Система анализирует доступный ей трафик и выдаёт
события с объяснением. Блокировка, изменение пакетов и управление фаерволом в объём
прототипа не входят. Промышленные протоколы внутри сети не являются первой целью.

Обнаружение будет комбинированным: сетевые признаки поведения и ограниченный набор
правил анализа HTTP. Реализация начинается с первого направления — портскана.

## Первый сквозной путь

```text
сетевой интерфейс Linux
        ↓
захват пакета и времени наблюдения
        ↓
декодирование Ethernet / IP / TCP
        ↓
наблюдение TCP: время, адреса, порты, флаги
        ↓
исполнение выбранного правила Suricata и его пороговых условий (план)
        ↓
объяснимый алерт → доставка в API → веб-интерфейс
```

Захват не принимает решения об атаке. Декодирование не хранит состояние детектора.
Детектор получает обычные Go-значения, а не библиотечные объекты захвата; это
позволяет проверять его на заданных наблюдениях без кабеля, root и ожидания времени.
TCP-наблюдение уже определено в internal/packet; формат алерта будет задан
при реализации исполнителя правил.

Сначала достаточно простого последовательного пути обработки. Внутренние очереди пакетов, воркеры
и параллельное декодирование добавляются при измеренной необходимости. Ограниченная
очередь доставки событий в отдельный API имеет другую задачу: изолировать захват
от задержек получателя. Нельзя
молча терять пакеты или менять порядок наблюдений ради увеличения скорости.

## Два пути анализа

```text
интерфейс / PCAP → декодирование пакета
                       ├─ TCP-наблюдение → условия TCP-правила и порог → алерт
                       └─ TCP-сборка → HTTP-разбор → условия правил → алерт
```

Портскан не ждёт сборки потока или HTTP-запроса. HTTP-правила получают разобранные
сообщения и нужные буферы, а не только адреса и TCP-флаги. Эти входы не объединяются
в универсальную структуру с полями на все случаи. Общими являются выходные алерты,
а не внутреннее состояние детекторов.

Для первого этапа поддерживается Ethernet без VLAN, IPv4 без фрагментации и TCP.
Другие типы канального уровня, VLAN, IPv6 и IP-фрагменты учитываются как
неподдерживаемые; усечённые и повреждённые пакеты учитываются отдельно. Они не
передаются в детектор как полноценные наблюдения. Перед расширением поддержки
добавляются соответствующие декодирование и проверки.

Перед HTTP-этапом определяются лимиты сборки, обработка повторов, нарушения порядка,
пропусков и перекрытий TCP-сегментов. Неполный поток отмечается как неполностью
проанализированный; отсутствие алерта не означает, что он безопасен.

## Структура проекта

Каталоги созданы по согласованному плану. Наличие каталога не означает, что
соответствующая возможность реализована. Уже работают CLI, открытие libpcap,
декодер TCP, последовательный диагностический цикл и отдельный загрузчик
правил; остальные части — план:

```text
cmd/
  absolert/                 запуск сенсора, флаги и завершение
  absolert-api/             запуск локального HTTP API
internal/
  capture/                  получение пакетов и статистика захвата
  packet/                   декодирование и собственные значения TCP-полей
  detect/
    portscan/               зарезервировано; отдельный алгоритм не реализован
  sensor/                   соединение захвата, декодирования и детекторов
  rules/                    загрузка, проверка и представление правил Suricata
  event/                    события и алерты для передачи за границу сенсора
  api/                      HTTP-обработчики и доставка обновлений в браузер
  storage/
    postgres/               сохранение событий и запросы к PostgreSQL
web/                        исходники React + TypeScript
migrations/                 SQL-миграции базы данных
configs/                    общие примеры конфигурации без секретов
docs/                       архитектура, план и описание стенда
```

Это один Go-модуль. Две точки входа позволяют запускать сенсор и API с разными
правами; они не требуют отдельных репозиториев и микросервисного конвейера.
Веб-интерфейс планируется на React и TypeScript; его Node-зависимости будут
изолированы от Go-сборки. Доставка реальных событий, Go API и встраивание UI
ещё не реализованы.

`cmd` отвечает за запуск и связывание компонентов. По мере появления логики
обработки пакетов она выносится в `internal/sensor`. Детектор не печатает алерты
и не зависит от HTTP или PostgreSQL. `internal/event` хранит предметные типы
событий, а не произвольные общие модели. Низкоуровневое наблюдение TCP относится
к `internal/packet`. Детекторы не получают объекты libpcap или HTTP-запросов API.

```text
capture + packet + detect → sensor → канал доставки → api → браузер
                                                   ↓
                                               storage
```

Стрелки показывают движение данных, а не точный граф Go-импортов. Конкретный
локальный транспорт выбирается перед этапом API. Браузеру и API не передаётся
сырой поток пакетов; они получают события, статус и счётчики.

Доставка событий не блокирует обработку пакетов: отправитель использует очередь
с ограничением числа и размера событий, ограниченным временем отправки и паузой
между попытками переподключения. При переполнении новое событие отбрасывается,
а накопительный счётчик потерь увеличивается. Статус и счётчики можно объединять
до последнего снимка; алерты не подменяются снимками. UI отличает свежий статус
от устаревшего или отключённого сенсора.

Первая версия не гарантирует сохранность событий при сбое процесса и не обещает
доставку ровно один раз. До добавления PostgreSQL определяются подтверждение
приёма и обработка дублей при повторной доставке. Ошибка записи не выдаётся за
успешное сохранение. Потери событий доставки и потери пакетов захвата — разные
метрики. API первоначально слушает только loopback; доступ к локальному каналу
сенсора ограничивается при выборе транспорта.

Юнит-тесты располагаются рядом с кодом (`*_test.go`). Синтетические фикстуры —
в `testdata` нужного пакета при появлении тестов. Пустые каталоги Git не хранит;
схема в этом документе остаётся ориентиром, без множества файлов `.gitkeep`.
Интерфейсы и заглушки методов заранее не создаются.

## Порядок подключения

1. Минимальный CLI сенсора с выбором интерфейса.
2. Захват и вывод TCP-полей в терминал для независимой проверки.
3. Выбранное TCP-правило: строгая загрузка, исполнение и алерт в терминале.
4. Go API и веб-страница для реальных алертов, статуса и счётчиков сенсора.
5. PostgreSQL, история событий и расширение детекторов.

Вывод в терминал — временная диагностика захвата. Создавать полноценный
консольный интерфейс до веба не требуется.

## Совместимость с правилами с начала разработки

Требование от 14 ноября: не создавать временный собственный язык сигнатур для
последующей замены. Для сигнатур исходным форматом служат выбранные правила
Suricata. Собственными остаются захват, разбор протоколов и исполнение условий.

Уже на подготовительном этапе выбирается небольшой набор существующих правил
SQLi/XSS. Для каждого фиксируются источник и лицензия, SID/rev, все используемые
условия, переменные сетей/портов, нужные HTTP-буферы и контрольные обмены.
Версия эталонной Suricata и её существенные настройки фиксируются вместе с набором.
Этот выбор предшествует проектированию TCP/HTTP-анализа и движка, но не блокирует
минимальный CLI и проверку захвата. Поддержка полного языка Suricata не заявляется.
Для выбранного правила должны исполняться все условия, влияющие на совпадение,
а не только извлечённая строка content. Неподдерживаемые условия — ошибка
загрузки с причиной, а не молчаливое пропускание.

Путь сигнатурного анализа:

```text
файл .rules → разбор и проверка → представление правила
                                       ↓
TCP/HTTP-наблюдение → исполнение условий → event.Alert → доставка и отображение
```

Условия работают с предназначенными им данными: TCP-флаги, направление потока,
сырые либо нормализованные HTTP-буферы. HTTP-правило нельзя корректно исполнить
простым поиском строки в каждом отдельном Ethernet-пакете. Нужные сборка TCP и
разбор HTTP выполняются до проверки условий соответствующего уровня.

Поведенческие детекторы и сигнатурные правила используют общий выход алертов,
но могут иметь разную внутреннюю логику. Состояние первого сценария задаётся
threshold выбранного правила. Нельзя выдавать собственную эвристику за
совместимость с Suricata keyword без проверки его семантики и версии.

В алерте сохраняется идентичность источника обнаружения. Для сигнатуры это SID
и ревизия, для собственного поведенческого детектора — его явный идентификатор;
фиктивные Suricata SID не назначаются. Хранилище и UI не должны зависеть от
конкретного исполнителя правил.

Критерий совместимости: выбранные правила дают сопоставимые результаты с
эталонной версией Suricata на положительных и отрицательных контрольных обменах.
Проверять также условия на границах TCP-сегментов. Версия формата и лицензия
источника правил фиксируются до включения чужих правил в репозиторий.

Справочные источники:
- https://docs.suricata.io/en/suricata-8.0.2/rules/intro.html
- https://docs.suricata.io/en/suricata-8.0.8/rules/http-keywords.html

Это справка по формату, а не уже утверждённая версия совместимости Absolert.

## Первый сценарий обнаружения

Исполнение начинается с ET Open SID 2002910 rev.6. Источник, лицензия, поднабор
загрузчика и дальнейшие проверки описаны в [RULES.md](RULES.md). Загрузчик уже
реализован, исполнение ещё не подключено.

Состояние и пороги определяются условиями выбранного правила. Оно считает
совпадения по источнику; это не подсчёт уникальных портов по паре источник/цель.
Нельзя подменять семантику threshold собственным алгоритмом и сохранять чужой SID.
Старый план отдельного поведенческого портскана не реализуется параллельно
правилу. Более широкое обнаружение добавляется после выбора подходящих правил.

Требования к исполнителю: корректные направление потока и маска флагов,
воспроизводимое время наблюдений, явные пределы памяти, очистка состояния,
учёт неполного анализа и сравнение с эталоном. Потери захвата и ошибки разбора
не смешиваются с алертами. Успешное подключение не обязательно.

## Выбор захвата

Выбраны libpcap и `github.com/gopacket/gopacket v1.7.7`. Захват открывается через
`pcap.OpenLive`: snaplen 65535, promiscuous mode выключен, ожидание чтения 100 мс.
На Linux библиотека использует неблокирующее чтение с ограниченным ожиданием;
цикл проверяет контекст между чтениями. Отдельная горутина чтения не создаётся.
Фактическое завершение на пустом живом интерфейсе ещё нужно проверить на стенде.

Входы с типом канального уровня, отличным от Ethernet, отклоняются при открытии.
BPF пока не включён для учёта неподдерживаемых пакетов. `ReadPacketData` копирует
данные, а декодер сохраняет только собственные значения. Полезная нагрузка не
выводится и не сохраняется; текущий `packet.TCP` относится только к поведенческому
пути. Байты для будущей TCP-сборки потребуют отдельного ограниченного хранения.

Текущие счётчики: прочитано, TCP, неподдерживаемые, повреждённые и усечённые.
Статистика libpcap выводится при остановке отдельно, без предположения, что
все платформы сообщают потери интерфейса. Построчный диагностический вывод
синхронный; это ограничение скорости до перехода к агрегатам раннего веба.

Первоначальная среда сенсора — Linux. Переносимость на Windows и macOS сейчас
не является критерием готовности. При использовании libpcap ожидается CGO;
конкретные команды установки зависят от дистрибутива.

Обработчик пакета не должен сохранять заимствованный буфер после его повторного
использования библиотекой. Нужные поля следует преобразовывать в собственные
значения либо обоснованно копировать данные с ограничением размера.

## Воспроизведение PCAP и время

Обработка принимает данные пакета, время захвата и сведения о захваченной и полной
длине независимо от источника. Чтение интерфейса и файла PCAP подают данные в один
путь декодирования и детектирования. Интерфейс Go для этого создаётся только когда
понадобится, а не ради предполагаемого расширения.

До сквозной проверки детектора добавляется чтение небольших синтетических PCAP.
Окна детектора определяются временем наблюдений, а не скоростью чтения файла;
дедлайны доставки и остановки относятся ко времени работающего процесса.
Обработка получает время явно. Перед реализацией окна фиксируется поведение при
убывающих временных отметках и очистка состояния при отсутствии новых пакетов.

Одинаковые PCAP используются для повторяемых проверок Absolert и эталонной
Suricata. Помимо совпадений проверяются отрицательные примеры и границы сегментов.
Результат сравнения относится только к выбранным правилам и настройкам, а не ко
всему языку. Исходные дампы частного трафика в репозиторий не добавляются.

## Дальнейшее развитие

- Сборка TCP-потоков с лимитами памяти, тайм-аутами и учётом пропусков.
- Разбор plaintext HTTP/1.1, отдельно от захвата и правил.
- Загрузка выбранных правил Suricata: поддерживаемые условия перечисляются явно,
  неподдерживаемое правило отклоняется с причиной. SID и ревизия входят в алерт.
- PostgreSQL для событий; версия схемы управляется миграциями.
- Отдельный Go API и браузерный интерфейс React + TypeScript; REST для запросов,
  SSE как кандидат для доставки новых событий. Интерфейс первоначально локальный.
- Минимальные права сенсора; API и UI не получают права захвата. Протокол локальной
  передачи событий и доставка при недоступности хранилища выбираются перед этапом API.

Это не конвейер микросервисов между каждым пакетом. Захват, декодирование и
детектирование остаются внутренними частями сенсора. Границы протоколов позволят
позже добавить HTTP/2, но TCP-сборка не заменяет его отдельный парсер кадров/потоков.
Расшифровка TLS в первый прототип не входит.
